# 豉油鸡机械臂仿真与控制工作台：可行性与架构 V0.6

日期：2026-11-03。交付范围为源码核查、架构和实施边界；没有创建完整三维应用、接入实机或部署新网站。

## 结论

需求可实现。建议沿用urdf-playground的Three.js、URDF和浏览器交互思路，新建模块化的本地工作台，将渲染、设备控制、状态采集、轨迹执行、视觉与MCP分开。优先交付真实三维场景、仿真控制、预设流程和结构化状态，再接实机与视觉。

简单场景、状态面板、截图和MCP属于成熟软件集成。主要工程难度是标定、可信反馈、连续轨迹、安全停机、异常恢复和视觉条件变化。高保真流体及烹饪结果预测属于独立研究任务，不纳入首版。

## 产品范围

### 三维场景

- SO-101准确关节模型与可替换机器人描述；自定义勺座、金属弯颈、汤勺。
- 锅、鸡的可辨识外观模型、汁液表面、外部泊位、托架与接液盘。
- 视觉外观与保守碰撞几何分别维护，避免鸡的漂亮网格掩盖翅腿/测量误差。
- 自由旋转、平移、缩放；俯视、侧视、腕部、固定工作相机；透明锅壁/剖视、坐标轴和轨迹开关。
- 显示目标姿态与反馈姿态，支持轨迹时间轴、阶段、暂停和历史回放。
- 每个场景声明单位、底座/锅/相机/工具变换、参数来源和版本。

### 状态和控制

- 每轴：目标与实测位置、跟随误差、速度、电流、电压、温度、启用状态、模式、设备错误、通信质量与数据年龄。
- 能力不支持的项目显示不可用，估算量显示估算；模拟、回放和实机都标明来源。
- 舵机Load字段不直接等于经过标定的N·m力矩；也不能把力矩使能位等同于独立安全保持。
- 关节与TCP点动、示教点保存、模型软限位、程序预览、作业取消、请求翻鸡和初始化模式。
- 单一运动控制权：手动、程序、模型不能同时写命令；切换时检查状态并取消过期作业。
- 页面上的停止为软件功能，不替代独立急停、制动和机械保持。

### 三种数据/执行模式

1. 仿真：允许手动、程序、模型工具调用；状态来自明确标注的模拟器。
2. 实机只读：只采集实际状态和相机图像，不下发运动。
3. 实机受控执行：仅在本地硬件与流程已验证、权限明确启用后，执行符合当前场景的有效计划。

日志回放是独立数据源，不写入设备。模式不能因切换页面、连接模型或重连自动变成实机执行。

## 建议架构

| 层 | 技术起点 | 职责 |
|---|---|---|
| 前端 | TypeScript、React、Three.js、urdf-loader | 场景、交互、状态、程序与录像/截图显示 |
| 本地服务 | Python、FastAPI、WebSocket | 状态快照、作业API、程序、日志、摄像头和鉴权 |
| 运动核心 | 现有NumPy FK/IK＋后续完整模型 | 轨迹、限位、工具坐标、碰撞、时间与版本校验 |
| 仿真适配 | 首期运动学；后续MuJoCo | 反馈生成、刚体/接触、故障注入 |
| 实机适配 | 所选Feetech/LeRobot接口＋近端控制器 | 单一串口所有者、状态读取、实际目标与看门狗 |
| 视觉 | OpenCV，按需求增加检测模型 | 标定、位姿与置信度，不直接调用舵机 |
| MCP | 官方Python SDK | 查询、规划、模拟、截图、作业状态与受限技能 |
| 独立保护 | 本地硬件与机械系统 | 急停、保持、防护及人员进入条件 |

前端从本地服务接收快照，MCP和相机也通过同一权威状态服务访问系统。模型和网页不各自建立一条绕过调度器的串口通道。

[FastAPI WebSocket](https://fastapi.tiangolo.com/advanced/websockets/)、[MCP Python SDK](https://github.com/modelcontextprotocol/python-sdk)、[MuJoCo Python](https://mujoco.readthedocs.io/en/stable/python.html)。

Web Serial可保留为简易调试入口，但浏览器兼容、权限和页面生命周期使其不适合作为整个设备平台的唯一运行中心。[MDN说明](https://developer.mozilla.org/en-US/docs/Web/API/Web_Serial_API)。

本地服务默认只对本机开放，控制入口鉴权并检查来源；若后续需要远程模型调用，另设计受限网关。不能仅因为接口地址是localhost就默认所有网页可调用。

已有可视化导出文件的沙盒iframe与CSP继续保留；它是演示载体，不通过削弱保护变成设备控制器。云端托管可展示演示前端，接在用户电脑上的USB、摄像头和设备执行服务仍需本地部分。

## 状态一致性与刷新率

### 每个状态必须能回答

- 来自哪个设备/模拟器/回放？是测量、估算、不可用还是过期？
- 时间戳、帧编号、数据年龄是多少？
- 关节映射、工具、标定、场景和轨迹版本分别是什么？
- 当前控制权和作业是什么？

建议前端30～60FPS作为显示目标，关节状态先以20Hz为起点，按实测总线吞吐和响应分布调整；温度等慢变量可1～2Hz，电流/错误按硬件能力和故障需求安排。这不是所有舵机字段都能以50Hz可靠读取的承诺。

渲染插值不能伪造新鲜反馈；陈旧数据要显式冻结、报警并阻止新的危险动作。不得在不同轴来自不同时刻时，默默拼成看似同步的完整姿态。

后台轨迹按单调时钟和固定步长/控制策略执行，不按浏览器渲染帧数决定步进。队列有上限、过期时间和作业世代；停止后旧命令不得稍后继续发送。USB断开、页面关闭、运行服务退出三种故障分别设计，不能以页面仍可显示为设备健康依据。

## 液面与淋汁的三个等级

| 等级 | 内容 | 首版建议 |
|---|---|---|
| 外观 | 锅内液面、波纹、勺内汁量、流柱/粒子和湿润效果 | 做 |
| 工程近似 | 勺容积与倾角、取汁/流出模型、重力弹道、碰撞落点、回流延迟、质量守恒 | 做受限版本，参数需标定 |
| 高保真多物理 | 晃液、破碎、飞溅、黏度、传热、蒸发与鸡肉软体/熟化 | 不纳入首版 |

工程近似需维护V锅＋V勺＋V空中＋V鸡表面＋V洒漏的账目，排除明确建模的蒸发/补液后守恒；避免每勺浇完自动凭空补满。锅口、锅底截面和鸡排液量应分别处理。液体显示可遮罩/裁剪鸡外观，不能简单让液面穿过鸡模型。

视觉好看不证明飞溅安全或实际剂量。MuJoCo的流体力模型不是倾倒热汁的自由表面求解器，官方也明确其范围不包含完整流体动力学。[官方范围](https://mujoco.readthedocs.io/en/stable/computation/fluid.html)。

## 程序执行：技能和受限配方

首版提供白名单指令，例如：取汁、移动到已确认点、倾倒、回到S、请求停靠、等待人工确认。配方用结构化JSON及可视化步骤编辑，供人和模型使用相同接口。

配方编译成绑定当前场景/工具/标定版本的轨迹，通过最终碰撞及速度校验后执行。计划有标识、摘要、有效期、作业状态与取消语义；重试不能重复浇一勺。运行中关键状态改变则计划失效，不能把旧计划重新用于新液位。

示意配方（不是已实现接口）：

```json
{
  "mode": "simulation",
  "recipe": "baste_then_park",
  "context_revision": "scene-revision",
  "steps": [
    {"skill": "baste", "target": "A", "volume_ml": 30},
    {"skill": "request_flip"}
  ]
}
```

30mL是期望参数，未标定时执行器不能承诺实际剂量。未知字段、无效点位、越界速度或实机未授权应被拒绝。

如果需要Python代码，另设仿真专用隔离工作进程，限制时间、资源和权限，代码只能调用代理技能接口；不能直接访问串口、任意文件、网络或安全配置。不能在网页主线程eval模型输出。

## MCP与模型动作

[MCP工具规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)支持结构化结果和图像内容，足以返回机器人状态、计划和截图。它不是硬实时总线、轨迹求解器或安全控制器。

建议先暴露：

- `get_robot_state()`、`get_scene()`：带来源与版本的结构化快照。
- `plan_skill(...)`：生成受限技能计划，返回失败原因/净空/关节范围等。
- `simulate_plan(plan_id)`：异步仿真作业，返回job_id。
- `get_job(job_id)`：查询执行状态，区分接受、运行、成功、取消与失败。
- `render_snapshot(view, state_revision)`：返回与指定状态对应的图像。
- `request_flip()`、`cancel_job(...)`：进入已有流程，不等于硬件急停。

默认模型只能在仿真里执行。后续实机入口只接受本地已明确启用的能力和当前有效计划，不能由模型自行开扭矩、修改限位、重校准、解锁泊位或解除保护。

模型工作循环应是：读状态 → 提出技能 → 模拟 → 查看截图与数值结果 → 修改计划。实机放行由独立的本地权限与设备状态决定，不由模型根据一张图自行认定安全。

### 渲染截图

首版可由工作台渲染器生成PNG，标注相机、状态版本和模拟时间；模型调用返回该图和同一快照的数值。无打开页面时，可使用独立渲染进程或MuJoCo离屏渲染。

截图任务不得占用舵机控制循环；预览视频、设备控制与给模型的低频截图分开。模型看不到网页，不意味着必须给它持续的视频；可在关键动作前后按需截图。

真实相机画面与模拟渲染明确区分。导入模型、代码、摄像头画面及识别到的文字是数据，不具有修改系统权限的指令效力。

## 摄像头与视觉调整

先接固定相机，做内参/外参、光照和时间戳，建立锅/工具/鸡的参考坐标。先检测锅位和鸡是否偏移，再考虑露出区域分割、表面颜色与液面估计。

识别输出应包含坐标系、观测时间、置信度、协方差/误差估计和标定版本。它先提出场景更新，待当前状态允许时，在零速边界更新后续计划，不直接连续改舵机目标。

可先只允许小范围修正；超出可信工作包络、遮挡、画面过期或置信不足时暂停请求人工确认。反光、蒸汽、油膜与鸡形状变化是主要现场工作量；漂亮的模拟图不能证明真实视觉识别可靠。

## 与现有V0.2～V0.5成果的关系

- 可复用几何假设、五轴FK/IK、工作/停靠路线生成、状态门槛与验证用例的思路。
- 当前JSON只是一组离线工况采样，必须在场景参数改变后重算，不能把改参数的界面套在旧动画上。
- 当前安全逻辑代码仅为离线规范，不是可直接交付的安全模块。
- 仿真中的电流、温度和载荷如没有可信模型，应显示不可用或明确的模拟值；不能装成舵机实测数据。
- 初始配置不同时，下发前核对真实校准和URDF映射，不能把模拟角度直接写入原始编码器目标。

## 工作量估算与实施顺序

以下为一名熟悉TypeScript/Python及机器人集成开发者的净工作量估算，不是报价或交付承诺；不含采购等待、硬件返工与高保真流体。

| 阶段 | 可验收交付 | 估算 |
|---|---|---:|
| A：三维仿真工作台 | 实体机械臂/锅/鸡/液面、自由视角、仿真点动、预设流程、状态、回放、截图 | 5～10人日 |
| B：执行与MCP | 作业/技能接口、最终轨迹校验、取消、版本、MCP状态/截图/仿真 | 5～10人日 |
| C：实机只读到冷态执行 | 总线采集、标定映射、初始化、控制权、看门狗、冷水闭环与故障验证 | 10～20人日 |
| D：固定相机辅助 | 标定、位置识别、场景修正、失效处理与现场调试 | 10～20人日 |

合计约30～60人日的工程量级。高保真流体、复杂现场视觉或安全产品化可能显著增加工作量。热态与独立保护的验证另行评估，不能承诺在上述范围自动完成。

第一阶段使用现有电脑，不预先采购独显或云GPU。预算5000元是硬件原型预算，不能同时视为完整软件开发人工预算。相机、模型推理费用、工业防护与长期运维单列。

## 第一版建议冻结的范围

做本地仿真模式的完整三维工作台：准确关节几何、锅/鸡/勺/泊位、基础液面与受限体积账目、自由视角、每轴状态来源、手动点动、浇汁/停靠流程、场景改动后重新规划、日志回放和截图。同步留出统一状态、设备适配器和MCP接口边界。

明确不宣称：虚构实机反馈、高保真飞溅、鸡肉熟化预测、模型自动控制真实热汤，以及已通过硬件安全验证。待仿真和截图闭环稳定后，再按只读→冷态受控执行→视觉辅助逐步扩展。
